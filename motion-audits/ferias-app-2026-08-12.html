MOTION AUDIT · DESIGN-MOTION-PRINCIPLES

ferias-app — Motion at the edge of too much

A mobile-first group travel organiser (meal planner, shopping, expenses) built with React 19 + Framer Motion. Rich motion intent, but vestibular safety is completely absent and several patterns compound into noticeable jank.

ferias-app / groupgrub React 19 · Vite · Framer Motion ^12.40 Audited 2026-08-12

10 Findings
2 Critical 4 Important 4 Opportunities

Overall

This app has real motion ambition — spring physics throughout, purposeful enter/exit patterns, well-scoped whileTap on interactive elements. The aesthetic is cohesive and the speed is mostly right. But two systemic failures undercut the entire effort: there is zero prefers-reduced-motion support anywhere in the codebase, which means the app is actively harmful for users with vestibular disorders, and there are several animate-pulse calls without Tailwind's motion-safe: prefix — the simplest fix in the codebase. Beyond those critical issues, stagger groups are overused on mount (three or four independent staggered lists fire simultaneously on the Expenses tab), and a 1-second delay in the GuestUpsellModal means users wait for content that should appear instantly. Fix the two critical issues immediately; the Important findings would push this from "good enough" to genuinely polished.

Jakub Krehel — Production Polish

Primary

Mixed — the spring foundation is solid but key UX moments (modal reveal, tab mount) feel unfinished.

What's working well

  • Spring params (stiffness 300–480, damping 25–38) are well-tuned for a mobile app — they feel native without being bouncy. ShopItem.jsx:25

Issues to address

Important Jakub

GuestUpsellModal: 1+ second delay before content appears

WhatThe modal renders immediately but its primary content items use delay: 1.0 + i * 0.07 — meaning the first line of real content appears after 1 full second. A separate element uses delay: 1.2. Users see an empty modal shell.

Why it mattersA 1s+ content delay breaks the psychological contract of a modal: the user dismissed their current flow to see this; making them wait for content reads as a broken experience. Jakub's polish standard is that content should be visible and readable within 300ms of the modal appearing.

Recommended motionUse delay: i * 0.04 starting from 0 (max stagger ~200ms for 5 items), or a single delay: 0.1 after the modal backdrop settles. Total content visible in under 300ms.

Important Jakub Emil

ExpensesTab: 4 independent stagger groups fire on every mount

WhatOn mount, ExpensesTab animates: the HUD block (delay 0), the balance block (delay 0.06), the settlements block (delay 0.1), each settlement row (i * 0.05), and each expense history row (i * 0.04). With 5 expenses the last row animates at 200ms. With 10 it's at 400ms.

Why it mattersExpenses is a frequently-visited tab. Users who check it multiple times per session see the same entrance sequence every time. Stagger is a first-impression pattern — it's AI-slop when applied to routine views.

Recommended motionRemove all mount stagger from the outer containers. Keep the AnimatePresence exit on individual rows (that's correct). If any entrance is needed, a single opacity: 0 → 1 on the tab root in 150ms is enough. Reserve stagger for newly added items only.

Issues to address

Important Emil

MealCard mount stagger fires on every tab navigation

WhatMealCards animate in with delay: index * 0.06 on every render. A Plano tab with 8 meal slots means the last card enters at 480ms. Every tab switch triggers this sequence.

Why it mattersEmil's frequency rule: if users trigger it 100s of times per day (tab switching qualifies), there should be no animation. The entrance stagger communicates "here's new content" — but re-navigating to the same meal plan is not new content.

Recommended motionRemove the stagger from MealCard's list-mount animation. Keep the spring enter for newly added meals (triggered by the add-meal action, not by tab mount). Use layout prop for reordering instead. Cards that are already in state should appear instantly.

Opportunities

  • whileHover scale: 1.005 on SlotCard is below human perceptual threshold (~1.02 is the minimum you'll notice). Remove it or raise to 1.015. Plano.jsx:126
  • whileHover x: 2 on MealPicker options: a 2px nudge is barely visible. Either commit (x: 6) or remove entirely — this is a frequent interaction. Plano.jsx:87
  • MealCard inline ingredient stagger (delay: ii * 0.04) is inside an already-staggered parent. When the meal card mounts, both staggers fire together — consider removing the inner one. MealCard.jsx:167
Through Emil's lens: The app treats every view as a first impression. Emil's core question — "should this animate at all?" — would eliminate most of the mount staggers. The interactions that deserve animation (add item, check off a purchase, submit a form) are exactly where the motion already lives. Move the restraint there.

Through Jhey's lens: The delight strategy is correct — ambient motion on rare transitions (onboarding, loading), satisfaction moments on key actions (checkbox, tap). The onboarding work is genuinely good. The only ask is to protect it with a reduced-motion guard so it doesn't cause harm.

Critical — systemic issues

Critical All lenses

Zero prefers-reduced-motion support — the entire codebase

WhatGrep across all .jsx files in src/ returns zero matches for prefers-reduced-motion. Every Framer Motion animation, every Tailwind animation class, every CSS transition runs unconditionally for all users.

Why it mattersUsers with vestibular disorders can experience nausea, dizziness, and migraines from motion — particularly from infinite looping animations (Onboarding floating emoji, App loading orbits). This is a WCAG 2.3 failure (AAA) and an ethical blocker. The infinite animations make it actively harmful.

Recommended motionAdd a useReducedMotion() hook from Framer Motion (import { useReducedMotion } from 'framer-motion') and use it to gate animations in components with repeat: Infinity as an immediate fix. Long-term: pass reduced-motion variants to all animate/transition props, or use Framer Motion's built-in useReducedMotion in combination with conditional animation props.

Critical All lenses

animate-pulse without motion-safe: prefix — 2 instances

WhatApp.jsx:185 and App.jsx:487 use Tailwind's animate-pulse directly. The codebase already uses motion-safe:animate-pulse correctly in ShopItem.jsx and motion-safe:animate-spin in ShoppingTab.jsx — so the pattern is known and simply missing in these two locations.

Why it mattersPulsing elements are among the highest-risk motion patterns for vestibular disorders. These two instances are loading screens — states the user may be stuck in for several seconds while data loads. A user with motion sensitivity will see continuous pulsing with no way to stop it.

Recommended motionReplace animate-pulse with motion-safe:animate-pulse on both elements. Two-character prefix change, immediate fix. No behavior change for users without the preference set.

Important Jhey All lenses

Infinite background animations without reduced-motion guard

WhatThree Framer Motion animations use repeat: Infinity with no prefers-reduced-motion guard: Onboarding.jsx:133 (floating emoji, 3.5s), App.jsx:178 (loading orbit, 3s), App.jsx:192 (secondary loading orbit, 1.2s).

Why it mattersInfinite looping motion is the highest-risk animation pattern for vestibular disorders. Loading screens can display for 5–15 seconds on slow connections. The onboarding screen is shown to every new user.

Recommended motionUse Framer Motion's useReducedMotion() hook. If shouldReduceMotion is true, replace animate with a static state and omit transition.repeat. Example: const shouldReduceMotion = useReducedMotion(); const floatAnim = shouldReduceMotion ? { opacity: 0.9 } : { y: [0, -8, 0], opacity: [0.8, 1, 0.8] };

07 · Lens reference summary

Lens referenced most: Jakub Krehel — Production Polish
This is a shipped consumer mobile app where polish is the primary metric. Spring physics, exit animations, and tactile feedback are exactly Jakub's domain. Emil was drawn in heavily because the frequency-gate failures are numerous; Jhey stayed selective (onboarding, loading) as intended.

To lean more Emil

Remove all mount-stagger from tab views. Make the rule explicit: animate only on user-triggered state changes, never on component mount for revisited views.

To lean more Jakub

Audit every modal and bottom-sheet for time-to-first-readable-content. Jakub's bar: the user should be able to read the primary message within 200ms of the overlay appearing.

To lean more Jhey

Add a delight moment to the settlement resolution ("all settled" state). An animated check or a confetti micro-interaction would celebrate a genuine user win — rare enough to justify it.

Non-negotiable (all lenses agree)

prefers-reduced-motion is the only finding where all three lenses have zero disagreement. Fix it first, before any other motion work.
